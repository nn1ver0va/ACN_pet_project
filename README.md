**"Зарядные станции ACN - рост загруженности, стагнация выручки"**

В проекте был проведен анализ данных сети зарядных станций ACN-Data (Caltech, январь-март 2019), в которых от месяца к месяцу растет занятость (occupancy), что, в свою очередь, не сопровождается ростом выручки (revenue). 

Проект ищет, за счет чего теряется потенциальная выручка - из-за растущей доли простоя после завершения зарядки (idle time) и/или отдельных станций с аномально долгими перебоями в работе - чтобы дать команде эксплуатации основание для конкретных решений, например, введения idle fee, добавление уведомлений в приложении о завершении зарядки или точечной проверки отдельных станций.

**Данные**

**Основной источник данных** - ACN-Data — открытый датасет сессий зарядки сети Caltech/JPL (США).
Сайт: ev.caltech.edu → раздел ACN-Data / acndata (доступен CSV-экспорт и API).

**Гранулярность:** одна строка = одна сессия зарядки. Данные охватывают период с января по март 2019, всего 2864 сессии, 53 станции зарядки.

**Ограничения:** отсутствует информация о тарифах (цена за kwh или за час), а также нет кодов ошибок или отметок о downtime станций. 

**Документированные допущения:**

- Был введен синтетический тариф - $0.25 за kWh и $1.5/час idle fee после завершения зарядки. Значения были придуманы для расчетов и явно помечены как synthetic, а не взяты из реальных данных.
- Uptime-прокси - поскольку у нас нет прямых данных о неисправностях станций, используется косвенный признак, а именно, аномально большой разрыв (gap) между окончанием одной сессии и началом следующей на той же станции. Важно отметить, что такой gap может означать как поломку станции, так и просто отсутствие спроса на нее, датасет не позволяет различить эти два случая напрямую.

**Вопросы и метод:**

**Основной вопрос:** почему рост occupancy не сопровождается ростом выручки? На какую метрику стоит опираться вместо occupancy, чтобы увидеть реальное положение вещей?

**Проверяемые гипотезы:**
- **H1** - рост occupancy объясняется ростом idle time, а не платной зарядки
- **H2** - часть станций имеет высокую occupancy, но низкий uptime
- **H3** - энергопотребление на сессию снижается вместе с ростом их числа

**Поддерживающие вопросы:**
1. Как расходятся во времени три метрики - occupancy, uptime, paid utilization? 
2. Какую долю занятого времени станции составляет простой (uptime)?
3. Различается ли динамика по станциям?
4. Есть ли станции с высоким occupancy, но низким uptime?

**Метрики:**

1. occupancy_rate - доля времени, когда станция физически занята, считаем как сумму (disconnect_time - connection_time) по всем сессиям станций, поделенную на общее доступное время за период
2. paid_utilization_hours - часы фактической зарядки за сессию: done_charging_time - connection_time
3. idle_time - часы простоя после окончания зарядки, но до отключения: disconnect_time - done_charging_time
4. idle_share - доля простоя в общем занятом времени, считаем как сумму idle_time / сумму occupied_time, помесячно
5. max_gap_hours - максимальный разрыв между окончанием одной сессии и началом следующей на той же станции (proxy-метрика для uptime)

**Инструментарий:**

- Агрегации: COUNT, SUM, AVG, MAX, GROUP BY, HAVING
- Оконные функции: LAG() - сравнение текущей сессии с предыдущей на той же станции
- JOIN - объединение occupancy и gap-анализа в одну итоговую таблицу
- CTE (WITH) - читаемая многошаговая логика запросов

**Результаты:**

**H1/H3 - сетевой тренд (январь-март 2019).** Доля idle time в занятом времени сети выросла с 47% до 52%, при почти неизменном числе сессий в месяц (985 - 931 - 948). Рост occupancy объясняется в первую очередь ростом простоя после зарядки, а не увеличением реальной платной зарядки (H1). Средняя энергия на сессию при этом снизилась с 10.4 до 9.4 кВт·ч, что говорит о том, что сессии становятся менее энергоемкими, но независимо от числа сессий, а не вместе с их ростом, как предполагалось изначально (H3).

**H2 - станция-аномалия.** Станция 2-39-139-28 выделяется одновременно высокой occupancy (~40%) и большим временем простоя (197 часов) при максимальном среди всех станций числе сессий (176), что указывает на как минимум один эпизод почти восьмидневного простоя - нетипичное поведение для активно используемой станции: высокая загруженность сама по себе не гарантирует стабильную доступность.

**Как воспроизвести:**

1. Исходные данные уже включены в `data/raw/acn_sessions_raw.csv` - их можно использовать сразу.
Если нужно получить данные заново «с нуля» (например, за другой период), то данные выгружаются через Power Query (Excel) прямым запросом к API ACN-Data (`https://ev.caltech.edu/api/v1/sessions/<site_id>`), с пагинацией через `_links.next.href` (Data → Get Data → From Other Sources → Blank Query; Home - Advanced Editor). Я использовала данный способ, поскольку прямое скачивание JSON с сайта было нестабильным и скачанные файлы обрывались.
2. Создай таблицу и загрузи данные - выполни `sql/01_create_table.sql` в PostgreSQL (через pgAdmin)
3. Проверь целостность данных - `sql/02_data_checks.sql` (дубли, количество строк/станций)
4. Запусти аналитические запросы по порядку:
   - `sql/03_h1_h3_monthly_trend.sql` → результат в `data/processed/h1_h3_monthly_trend.csv`
   - `sql/04_occupancy_by_station.sql` → `data/processed/occupancy_by_station.csv`
   - `sql/05_h2_gaps_analysis.sql` → `data/processed/h2_gaps_joined.csv`

**Инструменты:** PostgreSQL + pgAdmin, Excel/Power Query (для загрузки исходных данных через API ACN-Data).
